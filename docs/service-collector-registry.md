# The service collector registry

## What was wrong

**Three collectors belonged to no service, and so reached no screen.**

```
SECURE_SCORES
ORGANIZATION_CONFIGURATION
EXCHANGE_MAILBOX_CONFIGURATION
```

`deriveTenantSyncFreshness` iterates `SERVICE_COLLECTOR_REGISTRY`, not the
`SyncResourceType` enum. A collector with no owning service therefore contributes
to no service's counts, no freshness verdict and no `partialFailures` entry. It is
**invisible rather than mislabelled** — it cannot even be reported as unknown,
because nothing iterates over it to ask.

The consequence is the one that matters: Secure Scores failing on all five tenants
for seventeen days could not surface on any screen, no matter what was built on
the frontend.

### The cause was one word

```ts
collectors: readonly string[]
```

`string[]`, not `SyncResourceType[]`. So a typo compiled, a collector that no
longer exists compiled, and a collector missing from every service compiled. The
registry was a hand-maintained list of strings that nothing checked — and because
it iterates itself, what it omitted was unobservable from its own output.

This is the third instance of one fault in this subsystem: `users: any[]` is data
without provenance, `syncFreshness?:` is an optional sibling, and this is an
unchecked list that iterates itself. **In every case the correct thing was
available and the incorrect thing compiled.**

## What is here now

**The type.** `collectors: readonly SyncResourceType[]`, so a name that is not a
real collector is a compile error.

**A compile-time proof that nothing is unowned.**

```ts
type UnownedCollector = Exclude<SyncResourceType, OwnedCollector>
export type EveryCollectorHasAnOwningService = MustBeNever<UnownedCollector>
```

Add a member to `SyncResourceType` without giving it a service and `tsc` fails,
naming the member:

```
error TS2344: Type '"SECURE_SCORES"' does not satisfy the constraint 'never'.
```

**`as const satisfies` is load-bearing, not style.** A `: readonly
ServiceDefinition[]` annotation widens each `collectors` array to the full union,
which makes `UnownedCollector` resolve to `never` whatever is listed — a check
that always passes. This was verified rather than assumed: with the annotation
restored and `SECURE_SCORES` genuinely removed, `tsc` exits 0.

**A test for the half types cannot do.** Types cannot count, so they cannot catch
a collector owned *twice* — which double-counts it in service totals. Verified the
same way: with `SECURE_SCORES` owned by two services, `tsc` exits 0 and three of
the five tests in `service-collector-registry.test.ts` fail.

The test's reference list is `Object.values(SyncResourceType)` — generated by
Prisma from `schema.prisma`. That matters: a check built from the registry's own
contents would agree with it by construction and could never find this defect.

## Where the three went, and why

**`ORGANIZATION_CONFIGURATION` → Office 365.** It shares an access-contract entry
(`m365_organization_configuration`) with `DOMAINS` and `LICENSES`, both already
owned by Office 365.

**`SECURE_SCORES` → Entra ID**, on the evidence rather than the name. Its
access-contract key is `entra_secure_scores`, and of the eight other resource types
in its readiness workload `entra_security_configuration`, seven are already owned
by Entra ID. (`SECURITY_DEFAULTS` is the eighth and sits in Office 365 — a
pre-existing inconsistency between the two groupings, left alone.)

**`EXCHANGE_MAILBOX_CONFIGURATION` → Exchange, and it is a MISSING entry rather
than a stale one.** This was the question worth getting right, because the two
answers have different fixes. It is not a rename of `EXCHANGE_MAILBOX_SETTINGS`:

| | permission | endpoint |
|---|---|---|
| `EXCHANGE_MAILBOX_SETTINGS` | `MailboxSettings.Read` (Graph) | `GET /v1.0/users/{id}/mailboxSettings` |
| `EXCHANGE_MAILBOX_CONFIGURATION` | `Exchange.ManageAsAppV2` (Exchange Online) | `GET /adminapi/v2.0/{tenantId}/Mailbox` |

They have separate access-contract entries, and `tenant-sync.service.ts` collects
both — listing them side by side in the same phase table.

## What to check first when it breaks

**Symptom: a collector is failing in the database and no screen shows it.**

1. **Check it has an owning service.** `grep` it in `SERVICE_COLLECTOR_REGISTRY`.
   This is the failure this file exists to prevent, and `tsc` should now make it
   impossible — so if you find one, the compile-time check has been weakened.
   Confirm `SERVICE_COLLECTOR_REGISTRY` still ends with `as const satisfies
   readonly ServiceDefinition[]` and not a type annotation; the annotation
   silently makes the check vacuous.
2. **Check the caller is not excluding it.** `deriveTenantSyncFreshness` takes
   `excludedCollectors`, and `tenants.service.ts` passes every resource type whose
   readiness is `NOT_LICENSED` or `UNSUPPORTED`. An excluded collector is removed
   from the service's expected count entirely — it is neither a success nor a
   failure, by design. That is the correct behaviour for "we are not licensed to
   ask", and it is also indistinguishable from "fine", which is the open question
   below.
3. **Check which caller you are looking at.** There are two, and they behave
   differently. `tenants.service.ts` passes exclusions; `tenant-sync.service.ts`
   calls `deriveTenantSyncFreshness(syncStates)` with none. On that second path a
   licence-blocked collector is *not* excluded and will be reported as a failure.

**Symptom: a service's expected collector count changed unexpectedly.** Adding a
collector to the enum now forces it into a service, which raises that service's
`expectedCollectors` and can move its status from `SUCCESS` to `PARTIAL` until the
collector actually runs. That is correct — it is the registry telling the truth
about what it expects — but it will look like a regression on the day it happens.

## Open, and deliberately not built here

**The service-level status has no word for "we are not allowed to ask."**

`ServiceSyncStatus` is `SUCCESS | PARTIAL | RUNNING | PENDING | FAILED | STALE |
NOT_COLLECTED | UNKNOWN`. A licence-blocked collector is excluded upstream, so it
correctly does not count as a failure — but nothing then says *why* the service is
reporting on fewer collectors. Not-licensed is invisible rather than mislabelled.
Better than wrong; still not the product's thesis.

Two details for whoever picks this up:

- `collectorStatus` in `service-sync-freshness.ts` never returns `NOT_LICENSED`,
  `UNSUPPORTED` or `EMPTY`, even though `CollectorSyncStatus` declares them. So
  `notLicensedCollectors` and `unsupportedCollectors` in the output are always
  zero, and the `partialFailures` filter that excludes those statuses never
  excludes anything. The exclusion that actually happens is the caller's.
- The signal already exists at the point where it is not used.
  `classifyCollectionFailure` in `collection-field-state.ts` derives
  `NOT_LICENSED` from `lastErrorMessage`, and `collectorStatus` receives the same
  `PersistedSyncState` — it just checks only for auth failures. Making the status
  reachable is a few lines; deciding what the *service* should then say, and what
  the frontend should render, is the part that needs a product decision.
