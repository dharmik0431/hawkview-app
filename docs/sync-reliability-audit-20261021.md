## Concrete correction

`selectScheduledTenantWork` previously ranked each eligible resource by the earlier of both its last attempt and last success. A recent FAILED attempt following an old success could therefore jump ahead of truly overdue daily work. A failing synthetic case placed a 16-minute targeted retry ahead of a 26-hour overdue daily resource because the retry's last success was ten days old. The corrected ranking uses the clock that governs the eligible work: the attempt for FAILED and abandoned RUNNING rows, and the success for healthy rows. It leaves the daily/full-pass decision, 5-minute USERS interval, hourly eligibility, retry backoff, and failure exclusions unchanged.

## Remaining limits to a “bulletproof” claim

1. **Candidate-window fairness above 1,000 continuously due tenants.** `TenantSyncService.syncDueTenants` queries at most 1,000 eligible tenants ordered by ID before applying its resource-clock ranking. If the first 1,000 IDs remain eligible on every tick, later IDs cannot enter that window. The 1,000-tenant unit test exercises progress *inside* the window, not this case. A durable scan cursor or indexed due-work queue, with a disposable-database test above the cap and crash/restart cases, is the next scheduler-scale design package. The observed six-tenant organization does not establish that this case occurs in production.
2. **Cross-process overlap.** `runInSyncMemoryLane` is process-local. `claimTenantUsersLease` sets the USERS row to RUNNING but that row is marked SUCCEEDED after user collection, before all secondary collectors complete. A second process could claim the same tenant during a long secondary phase; the 15-minute stale-lease rule also permits reclaiming an unusually long USERS phase. A tenant-wide operation lease with fencing/renewal needs design and physical race tests before multiple API workers or rolling-deploy overlap can be called safe. This is a source-path risk, not an observed production overlap.
3. **Freshness and completeness are different facts.** A successful `SyncState` proves the bounded collector committed a success; it does not prove Microsoft returned every expected record. Each resource needs explicit completion, page/cap, source-time, and run-correlation evidence before the product can claim complete coverage. Do not convert missing/limited Microsoft evidence into a clean state.
4. **External and held coverage.** Five GreenTech MSP tenants lack the Microsoft P2/access conditions for full Entra RISKY_USERS collection; five SIGN_INS resources use limited non-premium fallback. GreenTech DIRECTORY_ROLES is intentionally OFF. These are not fixed by another scheduler retry, and no licence, consent, role, or tenant setting should be changed as part of this source repair.

The next bounded engineering step is to design and test cursor/fencing behavior against a disposable migrated database, then assess per-resource completion evidence. Acceptance requires both positive progress and falsifying cases: >1,000 continuously due tenants, concurrent workers, interrupted visits, backoff preservation, and exact post-release health. A single green cron response or a successful Secure Score row is insufficient.
