## Concrete correction

`selectScheduledTenantWork` previously ranked each eligible resource by the earlier of both its last attempt and last success. A recent FAILED attempt following an old success could therefore jump ahead of truly overdue daily work. A failing synthetic case placed a 16-minute targeted retry ahead of a 26-hour overdue daily resource because the retry's last success was ten days old. The corrected ranking uses the clock that governs the eligible work: the attempt for FAILED and abandoned RUNNING rows, and the success for healthy rows. It leaves the daily/full-pass decision, 5-minute USERS interval, hourly eligibility, retry backoff, and failure exclusions unchanged.

## Candidate-window scale package in local review

The ID-ordered query selected only the first 1,000 eligible tenants before resource-clock ranking. If those first IDs remained due each tick, a later tenant could never enter the window. The proposed durable `scheduled_sync_cursors` row stores only an opaque tenant-ID scan position and a compare-and-swap revision. Each tick scans at most the configured 1,000-row window, wraps by keyset when needed, and commits its position before collector work. A losing concurrent scan rereads the new position; a process crash after advancement resumes elsewhere on the next tick and eventually wraps. Post-cursor candidates receive priority over the wrapped prefix so old dueAt ties cannot recreate starvation. The 5-minute cron cadence, batch and candidate caps, retry rules, resource eligibility, and collector behavior stay unchanged.

The local synthetic test holds 1,001 tenants continuously due and proves tenant 1,001 is dispatched on the second scan after a service restart. Focused scheduler tests, backend TypeScript and Prisma validation pass. Two registered migrated disposable-PostgreSQL cases cover concurrent cursor revision rejection and actual dispatch beyond the 1,000-row cap; they have not run locally or in protected CI yet. This package is not deployed; the current production fleet count of nine active connected tenants makes it a future scale risk rather than an observed outage. It does not solve cross-process collection overlap.

## Remaining limits to a “bulletproof” claim

1. **Candidate-window fairness above 1,000 continuously due tenants.** The local cursor package above addresses this source-path risk but still needs protected CI, migration/release proof, and ongoing operational observation. The previously accepted 1,000-tenant unit test covered only progress *inside* the old window; the new 1,001-tenant test exercises crossing it. Neither the observed six-tenant organization nor the nine-active-tenant aggregate establishes a production scale incident.
2. **Cross-process overlap.** `runInSyncMemoryLane` is process-local. `claimTenantUsersLease` sets the USERS row to RUNNING but that row is marked SUCCEEDED after user collection, before all secondary collectors complete. A second process could claim the same tenant during a long secondary phase; the 15-minute stale-lease rule also permits reclaiming an unusually long USERS phase. A tenant-wide operation lease with fencing/renewal needs design and physical race tests before multiple API workers or rolling-deploy overlap can be called safe. This is a source-path risk, not an observed production overlap.
3. **Freshness and completeness are different facts.** A successful `SyncState` proves the bounded collector committed a success; it does not prove Microsoft returned every expected record. Each resource needs explicit completion, page/cap, source-time, and run-correlation evidence before the product can claim complete coverage. Do not convert missing/limited Microsoft evidence into a clean state.
4. **External and held coverage.** Five GreenTech MSP tenants lack the Microsoft P2/access conditions for full Entra RISKY_USERS collection; five SIGN_INS resources use limited non-premium fallback. GreenTech DIRECTORY_ROLES is intentionally OFF. These are not fixed by another scheduler retry, and no licence, consent, role, or tenant setting should be changed as part of this source repair.

The next bounded engineering step after the cursor package is a tenant-wide operation lease with fencing and renewal, tested against a disposable migrated database under concurrent workers and interrupted visits. Per-resource completion evidence then needs separate assessment. Acceptance requires positive progress and falsifying cases for >1,000 continuously due tenants, concurrent workers, interrupted visits, backoff preservation, and exact post-release health. A single green cron response or a successful Secure Score row is insufficient.
