## P0 — resumable Microsoft tenant onboarding (merged via PR #184; backend deployed; GAS and app-registration permission pending)

- New HawkView-managed tenants now continue from Microsoft administrator consent into one dedicated, durable route: `/tenants/{id}/onboarding`. The customer does **not** create another app registration. HawkView's multitenant home application remains the single application object; Microsoft administrator consent creates the corresponding enterprise application/service principal in the customer tenant. This follows Microsoft's multitenant application and admin-consent model: <https://learn.microsoft.com/en-us/entra/identity-platform/app-objects-and-service-principals> and <https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent>.
- The setup has three explicit stages. Stage 1 is the required standard HawkView application consent. Stage 2 is optional Exchange recipient enrichment: separate `Exchange.ManageAsAppV2` consent, followed by the existing generated tenant-specific Exchange RBAC script and a real HawkView verification probe. Stage 3 is optional Microsoft 365 report-name visibility: the administrator opens Microsoft 365 admin center → Settings → Org settings → Services → Reports, enables **Display concealed user, group, and site names in all reports**, waits for propagation, and lets HawkView verify it.
- The Exchange explanation is deliberately precise rather than absolute marketing copy. Microsoft documents that `Exchange.ManageAsAppV2` authenticates the application to the Exchange Admin API and that Exchange RBAC determines the actual cmdlets and objects available: <https://learn.microsoft.com/en-us/exchange/reference/admin-api-authentication>. HawkView activates enrichment only after verifying its custom role exposes exactly `Get-Mailbox`; it rejects a broader Entra directory role or another Exchange role group and never calls `Set-`, `New-`, or `Remove-` cmdlets. Consent alone is never presented as working access.
- HawkView does not silently change the Microsoft report privacy setting. The access registry adds the least-privileged application role `ReportSettings.Read.All` and the backend performs only `GET /v1.0/admin/reportSettings?$select=displayConcealedNames`, as documented at <https://learn.microsoft.com/en-us/graph/api/adminreportsettings-get>. `ReportSettings.ReadWrite.All` and `PATCH /admin/reportSettings` are intentionally absent. This preserves the truthful statement that HawkView can verify, but cannot modify, the setting. The customer administrator remains the human approval/change boundary.
- Progress is server-owned, not stored only in React/browser state. New `TenantConnection` fields record Exchange verification or explicit deferral, report-setting observation or explicit deferral, and onboarding completion. A versioned, strict onboarding DTO derives the next step exclusively from those durable facts. Closing the tab, losing internet, restarting the computer, using another device, reloading, or returning through the tenant directory reconstructs the same next action. Existing tenant connections are migration-backfilled complete so current MSPs are not blocked; newly created connections intentionally start incomplete.
- Microsoft consent is crash/replay safe. A new `MicrosoftConsentAttempt` table records one exact organization, optional tenant, initiating user, consent flow, hashed nonce, expiry, consumption time, and bounded result code. Standard Graph, tenant-discovery, and optional Exchange consent have independent attempts, so concurrent tabs cannot overwrite a shared state field. The signed state must match the durable flow/org/tenant record and an atomic consume succeeds once; expired, replayed, cross-flow, cross-organization, and duplicate callbacks fail closed. A failed or interrupted attempt does not corrupt prior progress; the user starts a fresh attempt and resumes.
- The tenant directory labels incomplete new connections **Continue setup**. The consent popup hands the durable onboarding URL back to its same-origin opener; if that handoff fails, the onboarding page remains usable in the callback tab. The page uses generation-guarded loads, validates every response with closed schemas, makes every action single-flight, and gives retry/defer choices without fabricating completion. Completion is idempotent and requires core consent plus an explicit verified/deferred outcome for both optional stages.
- Deployment prerequisites and order are strict: (1) add Microsoft Graph application permission `ReportSettings.Read.All` to the HawkView home app registration; do not add `ReportSettings.ReadWrite.All`; keep `Exchange.ManageAsAppV2` separate; (2) apply migration `20260823213000_add_resumable_tenant_onboarding`; (3) deploy the matching backend; (4) publish the matching frontend/GAS; (5) test a brand-new tenant through core consent, Exchange verify/defer, report verify/defer, crash/reload, duplicate callback, and final resume. Reversing migration/backend order can break startup, and publishing the strict frontend before the backend contract can leave setup unavailable.

- Historical numeric rows project correctly without a sync. A legacy snapshot without the new compact evidence remains usable but its usage-readiness dataset is `UNVERIFIED` until a normal collection stamps proof. Invalid new evidence is `PARTIAL`; the optional report datasets remain isolated from healthy SharePoint site inventory/settings. After collection, the existing field-state ledger materializes separate bounded SharePoint and OneDrive projection outcomes. Tenant listing reads only those two tenant-scoped compact rows and never loads or rescans the up-to-40,000-row usage snapshot.

A valid SharePoint report stays `READY` when Microsoft legitimately returns no OneDrive rows; that OneDrive dataset alone stays `PARTIAL`. Empty report responses, missing/invalid or mixed refresh dates, duplicate/missing stable report identities, tampered evidence/periods/counts, incomplete inventory-to-report matching, or unreported activity keep exact storage/deleted/inactivity metrics unknown. - The Exchange rule drawer removes the three repetitive empty object-history rows. It retains the validated snapshot observation as `Configuration collected by HawkView` and states once that Microsoft Graph `messageRule` does not provide object creation/modification timestamps or an actor.
- Opening a rule drawer now lazily requests a bounded related-audit candidate contract. The authenticated tenant service first enforces existing organization membership, then queries stored `M365AuditRecord` rows by organization, customer tenant, indexed 90-day event-time range, retention, and an exact four-operation allowlist. ## P0 incident repair — frontend tenant isolation across account switches

Status: implemented locally on `codex/p0-frontend-tenant-isolation`; unpublished and independently approved for combined release integration. No backend data, Supabase configuration, tenant, deployment, permission, or live state was changed.

- A current-main audit found that the backend tenant list and bundle queries enforce active HawkView organization membership from the bearer identity, but the long-lived frontend `QueryClient` used identity-independent keys and survived logout/login navigation. A second account could therefore render the previous account's still-fresh in-memory tenant result for up to five minutes without issuing a new API request. Separate tenant-bundle and topbar-name module caches were also keyed only by tenant identifier.
- The query client is now owned by an explicit Supabase-identity plus HawkView-organization cache scope. Before an identity transition is rendered, registered sensitive queries are synchronously cancelled and cleared; a keyed provider creates a fresh client for the new scope. Tenant list, tenant bundle, and dashboard query keys also contain that scope as defense in depth.
- Authentication bootstrap uses a monotonic identity-transition ticket. The previous HawkView session is cleared immediately when the Supabase subject changes or sign-out begins, and an older asynchronous bootstrap result cannot commit after logout or a different user signs in. Auth callbacks return before making additional Supabase auth calls.
- Tenant-detail snapshots and topbar tenant names use identity-scoped memory caches. A failed request may retain only a snapshot previously fetched within the same identity/workspace scope; it cannot fall back to another account's data. Authenticated API fetches explicitly use `cache: 'no-store'` to prevent browser HTTP-cache reuse.
- No tenant data or mock/demo provider is used as a production fallback. Existing local-storage sidebar/view preferences remain unchanged because they contain no tenant records.

Combined release validation covers A loading dashboard/tenant details, A signing out, B signing in within the five-minute query freshness window, a deliberately late A bootstrap completion, a failed B bundle request, browser back navigation to A's tenant URL, topbar name rendering, and direct backend organization-isolation checks. On the combined branch, all 75 frontend tests, the complete backend suite (239 passed and two intentional legacy SharePoint REST skips), root/backend TypeScript, frontend lint, Prisma validation with a non-production placeholder URL, both production builds, and `git diff --check` pass.

## Local release — MSP organization onboarding

Status: combined backend/frontend implementation on `codex/p0-msp-workspace-onboarding`; final independent QA **PASS (P0=0, P1=0)**. It is safe to publish as a draft PR but remains local, unpublished, unmerged, and undeployed. No migration, Supabase, tenant, consent, permission, Render, GAS, or other live-state mutation has occurred.

- A direct subject-authoritative signup still creates exactly one isolated organization and owner membership, but the organization now starts with an incomplete durable onboarding state. Bootstrap serializes on sorted provider-subject and normalized-email transaction advisory locks before its first identity read, and retries one unique race through the same locked reread. Simultaneous first calls therefore converge on the same user, membership, organization, and session. The existing generated slug remains an internal stable identifier and is never accepted by the onboarding/settings API. Bootstrap adds the closed `workspaceOnboarding` contract and returns only active memberships in active organizations.
- `POST /api/workspace/onboarding` requires the active founding `MSP_OWNER`, exact organization scope, a bounded MSP/organization name, optional syntactically valid DNS business domain, and a valid IANA timezone. Completion is one transactional compare-and-set with the workspace audit record. Identical retries are idempotent; a conflicting retry or concurrent change returns HTTP 409 rather than overwriting the winner.
- After initial setup, `PATCH /api/workspace/organization` allows any active `MSP_OWNER` in the explicit organization to edit name/domain/timezone, uses optimistic concurrency, preserves the slug, and records only changed field names in the audit log. Founder-only protection ends with initial setup; ordinary self-removal and last-owner safeguards remain. Before completion, another invited owner cannot complete setup or remove/demote the founder.
- Every workspace team/audit/settings operation now requires an explicit UUID organization context instead of selecting the first membership. Reads use `organizationId` in the query; writes use it in the body, except member deletion which uses the query. Reversed membership order cannot change scope. Notification preferences remain user-level and are not presented as organization-scoped.
- `GET /api/workspace/members?organizationId=<uuid>` returns the same explicitly selected active-owner organization as a closed profile view (`id`, `name`, informational/unverified business domain, timezone, and onboarding completion time), plus server-derived `canEditOrganization`. That capability is true only for a completed organization viewed by an active MSP owner; initial setup remains a separate founder-gated flow. The Admin Workspace therefore does not need to reuse the bootstrap profile for a different membership, infer authority, or depend on membership ordering.
- Tenant onboarding/consent creation requires a completed organization setup in addition to the existing active role checks. Invitees do not receive the founder's initial setup gate.
- Migration `20260820200000_add_msp_organization_onboarding` adds the bounded organization fields and founder relation. Every organization that exists when the migration runs is deterministically marked complete so established MSPs are not interrupted; the earliest active owner membership becomes the founder. Historic organizations without an active owner remain complete with no founder-edit authority until a future audited recovery flow.
- A business domain is optional descriptive organization metadata. Unicode format controls, IP literals, ports, backslashes, encoded URL forms, schemes, paths, credentials, and invalid DNS labels are rejected. API projections label it `UNVERIFIED_INFORMATIONAL`; HawkView does not claim DNS ownership or verification from this value.
- The protected frontend shell is blocked only by the explicit normalized bootstrap onboarding contract. A founder receives a compact, accessible first-login setup view before any tenant/product data renders; existing/backfilled organizations and invitees skip it only when the backend says `required: false`. Missing, malformed, inactive-organization, or cross-organization state fails closed. The internal slug is never requested or rendered.
- Workspace completion clears identity-bound caches, refreshes authenticated bootstrap, and lifts the gate only after durable backend completion. Subject+organization+generation-guarded cross-tab signals and bounded focus/visibility refresh prevent a stale pre-change bootstrap or Admin profile response from remaining final. Late responses, account switches, reversed organization membership order, and failed refreshes cannot reuse another identity or selected organization's state.
- The Admin Workspace requires one explicit URL-selected active-owner organization UUID for team/profile/audit reads and every organization-scoped mutation. Multiple-owner memberships require a deterministic selector rather than choosing the first membership. Profile fields and edit capability come from the exact selected-organization response; the editor appears only when `canEditOrganization` is exactly true, adopts external updates when idle, and reloads the generation-guarded selected organization after a save.

Deployment prerequisite: apply `20260820200000_add_msp_organization_onboarding` before starting the matching backend. Deploy the matching backend before publishing the frontend/GAS gate. GAS remains user-managed and must be pulled from merged `main` and published separately after backend health/migration verification.
