## P0 — Microsoft collector resilience and truthful incident handling (local, unpublished)

- A launch-readiness audit found a systemic trust defect: several Microsoft Graph collectors treated a temporary 429/5xx/timeout exactly like a durable configuration problem, and a user-collection failure after successful token acquisition could suspend the entire tenant connection. Conditional Access 500s were consequently shown as permission/policy problems even though no customer action could resolve them.
- Microsoft token and Graph failures now cross one closed classifier with stable reason codes for authentication, permission, throttling, Microsoft transient service failure, network timeout, delta reset, HawkView capacity guard, invalid Microsoft response, and internal failure. Only deterministic token-endpoint authentication rejection can mark the tenant connection unavailable. A collector failure after a token was issued remains scoped to that resource and never clears the previously verified permission projection.
- The common Microsoft request boundary retries only transport, 429, and 500/502/503/504 responses, at most three attempts, with bounded `Retry-After`, a fresh timeout and request ID per attempt, and an optional collector deadline. POST retries require an explicit idempotency declaration. Graph error projection retains only bounded Microsoft code/request identity, streams under an actual byte ceiling with cancellation, and never stores raw response bodies.
- Conditional Access and the shared Entra collector path, licenses, organization/domain inventory, groups/owners/members, security defaults, authentication-method collection/policy, mailbox inventory/settings/rules/configuration and usage, Management Activity sign-in fallback, SharePoint inventory/drives/settings, and SharePoint/OneDrive usage reports now use the same retry/error boundary. A transient Management Activity content failure can no longer be skipped and saved as an apparently complete Sign-ins result. Existing SharePoint response/page/record/deadline guards remain authoritative.
- Expired Microsoft users delta checkpoints (HTTP 410 / `syncStateNotFound`) now trigger one bounded full baseline rebuild. The full pass reconciles users not observed since the rebuild began as deleted and saves the new delta checkpoint; it does not require an operator reconnect or manual database repair.
- The five-minute scheduler can now retry a bounded set of idempotent tenant-level collectors with cost-aware exponential backoff. Stable authentication, permission, capacity, invalid-response, and HawkView-internal failures are excluded from hot retries. Temporary failures are `PENDING` for the first two attempts, keep prior data usable, and do not enter the action center. At the third failure they become a medium `refresh delayed` issue linking to synchronization status; they are never labelled `Review policies` or `Review permissions` unless the typed failure is actually permission-related.
- Focused resilience/scheduler/health tests pass **61/61** and the final complete backend suite passes **291 tests** with two intentional legacy SharePoint REST skips. Backend TypeScript, Prisma validation with a non-production placeholder URL, and the production backend build pass; `git diff --check` passes with line-ending notices only. The first complete-suite run found one stale assertion expecting the former generic Sign-ins code; that test now asserts `MICROSOFT_TRANSIENT` and automatic-retry copy. The repair is locally complete but remains unpublished pending independent QA.
- Scope is backend/tests plus this continuity record on `codex/p0-collector-resilience`. No schema, migration, new Microsoft permission, tenant consent, manual sync, Render/GAS configuration, commit, push, deployment, or live mutation is included.

## P0 — Entra sign-in entitlement and consent repair (local, unpublished)

- Microsoft 365 Business Premium includes Microsoft Entra ID P1. GreenTech's `Authentication_RequestFromNonPremiumTenantOrB2CTenant` response therefore must not be accepted as authoritative proof that the tenant lacks a premium license. Microsoft documents that Graph sign-in retrieval can return this response intermittently when the token has only `AuditLog.Read.All`; Microsoft requires both `AuditLog.Read.All` and `Directory.Read.All` so the service can evaluate tenant licensing reliably.
- HawkView now recognizes Entra P1/P2 only from a recent successful, tenant-and-organization-scoped `/subscribedSkus` service-plan projection. Canonical P1/P2 plan names and IDs are code-owned. Current enabled P1/P2 evidence is `PREMIUM`; a complete current inventory without either is `NON_PREMIUM`; stale, future, malformed, pending, or missing evidence is `UNVERIFIED`. An upstream “non-premium” string cannot override current P1/P2 evidence in readiness.
- The required Microsoft permission contract now includes Graph application permission `Directory.Read.All`. Premium tenants require `AuditLog.Read.All` plus `Directory.Read.All` for the full Graph source. Confirmed non-premium tenants require the existing Office 365 Management API `ActivityFeed.Read` fallback. Unknown entitlement requires both source permission sets until HawkView can verify the best source.
- The collector still tries the full Graph sign-in source first. When Microsoft returns the recognized non-premium response, the existing bounded `Audit.AzureActiveDirectory` fallback preserves continuity. A successful fallback is persisted as `PARTIAL`, never as complete Graph success: premium evidence produces a consent-shaped partial diagnostic, confirmed non-premium evidence states the P1/P2 boundary, and unknown evidence remains unverified. The existing incremental scheduler continues retrying the full source automatically.
- Release prerequisite outside the repository: add Microsoft Graph **Application** permission `Directory.Read.All` to the actual HawkView managed app registration. Existing connected tenants must then repeat HawkView administrator consent so their enterprise-app grant/token includes the new role. Customer-managed connector apps need the same permission and re-consent in their own registration. No live app-registration, consent, tenant, sync, schema, or migration action is included in this local repair.
- Local validation: focused entitlement/collector/readiness/consent tests pass **37/37**; the complete backend suite passes **279 tests** with two intentional legacy SharePoint REST skips. Backend TypeScript, Prisma validation with a non-production placeholder URL, the production backend build (outside the Windows sandbox only for linked esbuild traversal), and `git diff --check` pass. Scope is backend/tests plus this continuity record on `codex/p0-signin-entitlement-routing`; it remains uncommitted and unpublished pending review.

## P0 — new-tenant Sign-ins provisioning reliability (merged)

- A live onboarding demo exposed `SIGN_INS` as failed while the same new tenant's Microsoft 365 Audit subscriptions were still being provisioned. Code diagnosis proved the full and incremental synchronization paths start Sign-ins and Microsoft 365 Audit concurrently. Tenants without Microsoft Entra ID P1/P2 cannot use the Graph sign-ins endpoint and rely on HawkView's bounded `Audit.AzureActiveDirectory` Management Activity fallback. On a new tenant, Sign-ins could check that subscription before the audit collector enabled it and persist an expected Microsoft provisioning state as a failed collection.
- Expected audit-subscription provisioning now remains `RUNNING` with the explicit code `sign-ins-audit-subscription-initializing`, zero consecutive failures, and an automatic scheduled-retry message. Readiness therefore reports `INITIALIZING`; tenant health and the action center no longer present it as a collection failure or publish a failure incident. Genuine permission, tenant-configuration, network, and upstream failures still follow the existing failed-collector path.
- The Management Activity collector now starts `Audit.AzureActiveDirectory` first for a new tenant, ahead of Exchange/SharePoint/General audit subscriptions. Microsoft's global 15-minute subscription-start cooldown remains unchanged and database-serialized. This makes the limited-license Sign-ins source eligible at the earliest scheduled retry without adding a Microsoft call, permission, consent, schema, migration, manual sync, or faster polling loop.
- Validation passed the complete backend suite with 270 tests passed and two intentional legacy SharePoint REST skips, including three new Sign-ins lifecycle regressions; focused Sign-ins and Management Activity coverage passed 26/26. Backend TypeScript, Prisma validation with a non-production placeholder URL, and `git diff --check` passed. Published and merged through PR #171; current base for the follow-up repair is merge commit `96927c9c5b66e48cc9e4a3114e32d46f9ead10ff`.

- Affected-service chips now recognize Sign-ins/directory failures as Entra, Microsoft 365 Audit as M365, Exchange collectors as EXO, and SharePoint collectors as SPO. An unaffected chip says only that no issue was reported in this tenant summary; it no longer claims the whole service is healthy.

## P0 — backend bootstrap identity isolation (local, unpublished)

- Normal signup/bootstrap no longer treats a case-insensitive email match as proof that two authentication identities are the same. An existing `authProviderUserId` subject is authoritative. Accepted accounts, legacy email-only profiles, and subject/email collisions fail closed without changing the stored provider subject or inheriting memberships.
- A direct signup with a new provider subject and email creates its own isolated organization and owner membership through the existing first-workspace flow.
- The only email-based bootstrap bridge retained is an explicit unclaimed pending invitation: no stored provider subject, `inviteSentAt` present, `inviteAcceptedAt` absent, and an active membership in an active organization. This uses the durable invitation state already written by HawkView and adds no schema or migration. There is currently no durable invitation-token digest or invitation expiry in HawkView, so broader account-recovery/relinking is intentionally unsupported and must use a future audited administrative recovery design rather than email matching.
- Workspace administration now resolves the acting owner only by provider subject; its previous email fallback is removed. It rejects a disabled subject-linked owner before team reads, audit-log reads, or administrative mutations, and refuses to turn an accepted or legacy email-only profile into a pending invitation. Notifications require a non-disabled subject-linked user and active organization membership. Tenant-list sign-in/audit aggregates and tenant-bundle sync-state/daily-audit-usage reads now include the already-authorized organization ID in addition to the customer tenant ID. The existing tenant lookup and Changes timeline/detail queries were audited and already derive scope from active organization membership/provider subject.
- Supabase's signed access-token contract has no authoritative email-confirmation timestamp/boolean. HawkView therefore does not trust `user_metadata.email_verified` or similar user-controlled fields. It now requires the signed permanent-session boundary: UUID provider subject, `authenticated` role/audience, `is_anonymous=false`, `aal1` or `aal2`, and a UUID `session_id`. Supabase's documented behavior is that Confirm Email yields no session before confirmation; if Confirm Email is disabled, Supabase explicitly treats the address as implicitly confirmed. The live project setting was not independently changed or queried by this repair. Calling Auth `getUser` on every HawkView API request was rejected because it would replace local signed-JWT verification with a remote request on every request without adding a stable signed claim.
- Regression coverage includes isolated direct signup, explicit pending invitation acceptance, accepted/legacy/non-member/disabled invitation rejection, subject-authoritative bootstrap, subject/email collision with no mutation, disabled-account no-mutation behavior, workspace-admin email-fallback/invitation-state/disabled-owner rejection, notification subject enforcement, organization predicates on tenant-list/bundle secondary evidence queries, permanent-session claim validation, anonymous/malformed-session rejection, and proof that user metadata cannot manufacture confirmation.
- Initial independent QA found **P0=0, P1=2**: disabled subject-linked workspace owners were not rejected inside `ownerContext`, and the token verifier did not explicitly enforce Supabase's permanent-session boundary. Both are repaired locally as described above. The final full-suite QA then found one stale Exchange rule test double still expecting the former tenant-only daily-usage unique lookup; that fixture now asserts the production `findFirst` query includes organization ID, customer tenant ID, and usage date. Production scoping was not reverted.
- This repair is backend/tests/documentation only from `codex/p0-backend-identity-isolation`. It is unpublished, not deployed, and has made no database, Supabase, Microsoft, tenant, consent, Render, or GAS change. Local validation passes the complete backend suite with 239 tests passed and two intentional legacy SharePoint REST skips; the focused auth/isolation suite passes 26/26. Backend TypeScript, Prisma validation with a non-production placeholder URL, the production backend build, and `git diff --check` pass. The backend slice was independently approved for this combined release integration.

## P0-6.3 — Entra authentication-registration reliability (merged)

- Live diagnosis found `AUTH_REGISTRATIONS` returning Microsoft Graph HTTP 403 even though HawkView already has the required read permissions. Microsoft documents the bulk `userRegistrationDetails` report as a premium Entra reporting capability; non-premium tenants can return the exact code `Authentication_RequestFromNonPremiumTenantOrB2CTenant`.
- The backend now reads only a bounded, safe `error.code` from Microsoft Graph. It falls back to the existing per-user authentication-method source **only** for that exact non-premium code. `Authorization_RequestDenied`, missing consent, arbitrary 403 responses, malformed bodies, and unknown codes continue to fail visibly rather than being misclassified as licensing.
- The fallback uses the already-required `UserAuthenticationMethod.Read.All` and `User.Read.All` application permissions. It adds no permission or consent. It first reads a fresh bounded Graph user inventory rather than trusting a potentially stale HawkView database copy. User discovery is capped at 50 pages and 20,000 users; authentication-method JSON batches contain at most 20 users and are capped at 1,000 batches, 2 MiB per response, 30 seconds per request, and ten minutes total. Repeated pagination, malformed/duplicate/incomplete responses, partial batches, limits, and timeouts prevent the authoritative baseline from advancing.
- Bulk collection and fallback share one `runSnapshotSync` boundary. A non-premium bulk response no longer writes an intermediate failed resource state or notification before a successful fallback; one complete result is saved once. This introduces no generic five-minute per-user poll: it runs only when the existing authentication-registration resource is collected through full inventory or exact audit reconciliation.
- Backend-only scope: `tenant-sync.service.ts`, a focused auth-registration regression suite and package script, plus this PM record. No frontend/Figma, schema, migration, permission, consent, tenant, Render, or GAS change is included.
- Final local QA: PASS, with no known P0/P1 release blocker. Auth-registration passed 12/12; adjacent backend suites passed 149 tests with two intentional legacy SharePoint skips; root/backend TypeScript, Prisma validation with a non-production placeholder URL, backend production bundle, the unchanged frontend/root production build, and `git diff --check` passed. Published and merged in PR #157; current `main` is merge commit `a5e460d0b7ed715c0eac84d2b0bbe9c689cb2d98`. This P0-7 task did not independently verify Render deployment state.
- Scale limitation: a 20,000-user non-premium tenant can require up to 50 user-discovery pages and 1,000 method batches for one complete run. This is bounded and acceptable for the current prototype/demo, but not a promise of economical 1,000-tenant operation. Before broad beta, persist the detected reporting capability and add per-tenant request/latency metering plus audit-trigger coalescing/cadence controls.

## P0-7 — truthful SharePoint/OneDrive data contract (local, unpublished)

It uses only the already-stored Graph site inventory, `/admin/sharepoint/settings`, SharePoint D180 usage report, and OneDrive D30 usage report. It adds no Microsoft request, permission, consent, schema, migration, or collector cadence.

It exposes the currently supported tenant controls in bounded groups: external sharing/domain restrictions, access/session controls, storage/lifecycle, site creation, collaboration/content, sync restrictions, notifications, and timezone.

Missing or unsuccessful report collection fails closed to unavailable/null rather than a fabricated zero.

## Product objective

HawkView is a read-only Microsoft 365 multi-tenant investigation and visibility product for MSPs and administrators. Phase 1 must show important tenant, identity, permission, policy, application, Exchange, SharePoint, and security changes; retain collected sign-in and audit evidence for approximately six months; and clearly distinguish Microsoft-supplied facts from HawkView inferences. Phase 2 may add tenant-changing actions similar to CIPP, but Phase 2 is not active.

Initial market: United States and Canada. Pricing and 1,000-tenant scale work are intentionally deferred until the prototype and evidence quality are ready.

## P0 incident repair — frontend tenant isolation across account switches

- No tenant data or mock/demo provider is used as a production fallback. Existing local-storage sidebar/view preferences remain unchanged because they contain no tenant records.
